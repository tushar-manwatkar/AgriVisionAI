# AgriVisionAI

**A clearer first look at plant health.** AgriVisionAI is a web app that checks leaf photos for visual patterns associated with supported plant conditions. It returns a likely match, confidence score, alternative matches, and care information when available.

> Results are visual guidance, not a confirmed diagnosis. Consult a local agricultural expert about serious or uncertain concerns.

## At a glance

- Upload a leaf photo or capture one with a camera.
- Review a predicted condition, confidence score, and other possible matches.
- Explore condition information, care steps, and prevention notes.
- Revisit recent checks saved in the current browser.
- Use light or dark appearance.

The classifier is organized around 38 labels from 14 plant groups. The browser accepts common image formats up to 16 MB; the API accepts PNG, JPG/JPEG, GIF, WEBP, and BMP files up to 16 MB.

## How it works

```text
React + TypeScript web app
        │
        │ image upload
        ▼
Flask API
        │
        ├── EfficientNetB0 model
        └── condition and care information
        │
        ▼
Prediction, confidence, and related guidance
```

The API resizes images to 224 × 224 pixels and runs the model when the trained model files are available.

## Run locally

### Requirements

- Python compatible with the TensorFlow version pinned in `backend/requirements.txt`.
- Node.js 18 or later and npm.
- The trained model files in `backend/model/saved_models/` for real model predictions.

Start the backend and frontend in separate PowerShell terminals from the project folder.

### 1. Start the backend

```powershell
Set-Location backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
python app.py
```

The API runs at `http://localhost:5001`. Check that it is responding at `http://localhost:5001/api/health`.

### 2. Start the frontend

In a second terminal:

```powershell
Set-Location frontend
npm install
npm run dev
```

Open the address printed by Vite (normally `http://localhost:5174`). In development, Vite forwards `/api` requests to the backend on port `5001`.

For a deployed frontend, set `VITE_API_URL` to the backend API base URL, including `/api`, for example `https://your-api.example.com/api`.

## Model files and prediction behavior

The backend loads these files:

- `backend/model/saved_models/best_model.keras`
- `backend/model/saved_models/class_names.json`

Keep both files from the same training run so model outputs map to the correct labels. If the model is missing or cannot be loaded, the API currently returns placeholder predictions. Placeholder results are not generated by a trained model and should not guide plant-care decisions.

Check `GET /api/model/info` and confirm `model_loaded` is `true` before relying on predictions. To prepare data and train the model, see [TRAINING_GUIDE.md](TRAINING_GUIDE.md).

## API

All endpoints use the `/api` prefix.

| Method | Route | Description |
|---|---|---|
| `GET` | `/api/health` | Check API availability |
| `GET` | `/api/classes` | List supported class labels |
| `GET` | `/api/disease/{label}` | Get care information for a label |
| `POST` | `/api/predict` | Predict from a multipart form with an `image` file field |
| `POST` | `/api/predict/base64` | Predict from JSON containing an `image` base64 value or data URL |
| `GET` | `/api/model/info` | Check model status and details |

A successful prediction returns `primary_prediction`, `all_predictions`, and `treatment`. The multipart upload route also returns `image_info`.

## Storage and privacy

Images uploaded to `POST /api/predict` are saved in `backend/uploads/`. The current API does not delete them automatically. Recent checks and image previews are stored in the current browser’s local storage; they are separate from the backend’s uploaded files.

## Deployment

Deploy the backend as a Railway service and the frontend as a Vercel project from the same GitHub repository.

### Railway backend

Create a Railway service from the repository and set its root directory to `/backend`. Configure:

- **Build command:** `pip install -r requirements.txt`
- **Start command:** `gunicorn --config gunicorn_config.py app:app`
- **Healthcheck path:** `/api/health`
- **Variables:** `TF_CPP_MIN_LOG_LEVEL=2` and `CORS_ORIGINS=https://your-app.vercel.app`

Replace the CORS origin with the exact Vercel site origin, without a trailing slash. Railway provides the `PORT` variable; `gunicorn_config.py` uses it automatically. Include the matching model and class-label files from `model/saved_models/` in the backend deployment.

### Vercel frontend

Import the same repository as a Vercel project and set the root directory to `frontend`. The existing `vercel.json` configures the Vite build and `dist` output. Add this environment variable in the Vercel project settings for the Production environment (and Preview too if previews should use the API):

```text
VITE_API_URL=https://your-railway-service.up.railway.app/api
```

Replace the example host with the Railway public domain. Redeploy the frontend after changing this variable. The local `frontend/.env.production` file is ignored by Git; set the Vercel variable in the Vercel dashboard.

Uploaded image files are stored on the backend filesystem and are not deleted automatically. Railway's filesystem is ephemeral unless a volume is configured, so files may disappear when the service is redeployed or restarted.
